# Digital Mana Badi — Login & Account Security Architecture

Status: Approved product decisions; implementation specification
Last updated: 2026-11-17

## 1. Scope and implementation guardrails
- Preserve approved UI, modules, navigation, footer, social ribbon, and existing functionality. Login/security work is additive except that authentication bypasses must be removed.
- The current site is a frontend preview. Firebase Authentication and Firestore are not connected. No localStorage flag or frontend-only check may be represented as real authentication or authorization.
- Use only the role label "Head Master"; never use "Principal".
- Prefer Firebase Spark/free-tier-compatible services. Do not introduce paid services, Cloud Functions, external APIs, or unnecessary Firestore reads/writes without explicit approval.
- Enforce access with trusted authentication and Firestore Security Rules; hiding UI controls is not security.

## 2. Roles and login identifiers
| Role | Daily login identifier | Account creation / approval |
|---|---|---|
| GI Super Admin | Registered email + password | Official account only; no public self-sign-up |
| Head Master | School official email + password | Created/enabled by GI Super Admin |
| Teacher | Registered mobile + password | Created and managed by Head Master |
| Parent | Registered mobile + password | Parent self-links child records using the agreed school-record matching flow |
| Alumni | Registered email + password | Open registration request; Head Master approval required before activation |
| Donor / Sponsor | Registered email + password | Open registration request; Head Master approval required before activation |

Alumni and Donor/Sponsor remain distinct account roles even if the current preview presents a shared entry point.

### Teacher account details
- Teacher ID format: year + teacher number, e.g. 202601.
- ID is generated by the Head Master workflow, unique within a school, and never recycled.
- Teacher ID is a school record identifier, not the daily login identifier.
- Profile includes name, teacher ID, registered mobile, optional email, subject/department, designation, assigned classes, joining date, optional photo, and account status.

### Parent account details
- Parent signs in using the registered mobile number and password.
- First-time linking uses the school record: school + academic year + class/roll or Student ID + date of birth + registered guardian mobile.
- No OTP is required for the agreed child-linking flow; apply rate limiting, attempt logging, temporary lockout, and non-enumerating responses.
- One Parent account can link multiple children. More than one guardian mobile may be associated with a student through separate guardian relationships.
- Parent sees only linked children. No Head Master approval is required for a valid parent-child link.

### Alumni and Donor/Sponsor
- Registration is open as a request, not immediate dashboard access.
- Head Master approval is mandatory before account activation.
- Pending/rejected accounts cannot enter their dashboards.
- Neither role can view private student or parent data.
- The app does not collect or process donations/payments.

## 3. First-time setup and profile
- Every user provides/has a profile name and gender preference once during account setup/profile creation; it is editable in profile settings.
- Gendered address must remain respectful: use "గారు" for male/female; if the user does not specify, use the name without a gendered suffix.
- After account verification, user sets an account password and may set an optional four-digit local app-unlock PIN.
- PIN is device-local and only for quick app unlock. It is not a replacement for the account password and cannot authenticate a new device.
- PIN must never be stored as plaintext in localStorage or Firestore. Use a salted, deliberately slow derived verifier in device storage; clearly treat this as a convenience lock, not strong remote authentication. Do not claim browser storage is tamper-proof.
- PIN recovery requires re-verifying the account using the role-specific recovery method, then setting a new PIN.

## 4. Password management and recovery

### Forgot Password
- GI Super Admin, Head Master, Alumni, and Donor/Sponsor: send a time-limited, single-use reset link to the registered email through Firebase Authentication.
- Teacher and Parent: verify their existing school records and registered mobile before allowing a password reset. Do not require an email address for these roles.
- Teacher verification uses registered mobile + Teacher ID + school association.
- Parent verification uses registered mobile + linked/known child record information (Student ID or class/roll + date of birth), scoped to the correct school and academic year.
- Do not expose whether a phone number, student, teacher, or account exists through public error messages.
- Verification must be rate-limited and enforced by trusted server-side logic. Only after successful verification may the Firebase account credential be changed.

### Change Password
- Available from authenticated Profile / Security Settings.
- Require current-password reauthentication or an equivalent trusted account verification.
- Require new password and confirmation; show validation and success/failure states.
- On password reset/change, revoke or refresh sessions according to the security policy; never log passwords.

### Technical blocker to resolve before live implementation
Firebase Authentication does not natively provide a Mobile Number + Password sign-in method. The approved Teacher/Parent UX must be implemented with a secure phone-to-auth-account mapping or a different trusted authentication design. Do not use a predictable/fake email address, public phone lookup, frontend-only password checking, or expose mapping records. Decide a Spark-compatible, secure approach before claiming mobile/password login is live.
Likewise, secure school-record-based password recovery requires a trusted verification path. Do not treat client-side form matching as sufficient.

## 5. Failed login protection
- Allow five consecutive incorrect password attempts.
- Display five attempt indicators/dots. Each failed attempt highlights one dot in red.
- After the fifth failed attempt, temporarily block login for 30 seconds and show a visible 00:30 countdown.
- When the 30 seconds finish, reset the five-attempt indicator and allow another attempt.
- Reset the failed-attempt count after successful authentication.
- Enforce attempt counting and lockout in trusted server-side logic, not only in browser state; browser refresh, storage edits, or changing device time must not bypass it.
- Use generic failure messages and rate limiting to reduce account enumeration and automated guessing.

## 6. Device and session policy
- Single active device per account.
- A successful login on a different device replaces/revokes the previous device session; the previous device must not continue accessing protected data.
- Logout applies to the current (only active) device session.
- No automatic inactivity expiry; keep the authenticated session until explicit logout or security revocation.
- Security revocation must still end sessions when an account is disabled, credentials are reset, or an administrator/security action revokes access.
- Remember only the registered email/mobile login identifier locally after logout. Never remember the password.
- A PIN unlock is allowed only on the same registered active device. A PIN must not bypass a revoked session or unlock a new device.
- Enforcing single-device access requires trusted session coordination and authorization checks on protected data. A local device ID alone is insufficient.

## 7. App-close / reopen PIN lock
- If the user has an active authenticated session and closes, backgrounds, or reopens the app, show the four-digit PIN lock before revealing the dashboard.
- Correct PIN returns to the existing dashboard without a fresh password login.
- Wrong PIN attempts are locally throttled; account-level password lockout remains a separate server-side control.
- Logout clears the authenticated session and returns to full account-password login; the remembered login identifier may remain.
- Browser/PWA lifecycle events differ from native app lifecycle. Implement and test page hide, reload, browser close/reopen, installed PWA reopen, and device restart. Never promise that a web page can detect every force-close event; persist a locked-on-resume state and require PIN on the next app launch.
- If PIN storage is unavailable or corrupted, require full account reauthentication rather than silently bypassing the lock.

## 8. Dynamic welcome and inspiration
- After every successful new login, select a greeting and one original quote using role + local time slot + app language.
- Time slots: morning, afternoon, evening, night.
- Role-specific themes: GI Super Admin (vision/leadership/progress), Head Master (education/school growth), Teacher (learning/teaching), Parent (child growth/family), Alumni (memories/gratitude), Donor/Sponsor (service/humanity).
- Maintain multiple Telugu and English greetings/quotes per role and time slot; avoid recently repeated selections locally.
- Reopening an existing active session with PIN does not create a new login greeting. A new authenticated login after logout does.
- Keep quote selection local; no Firestore read/write is needed for each login.

## 9. Security, privacy, and role access
- Firebase Security Rules must enforce school isolation and role permissions.
- Head Master manages only their school; Teacher sees only assigned classes/subjects; Parent sees only linked children; Alumni and Donor/Sponsor see only approved community information; GI Super Admin has platform-level controls.
- Account status (pending, approved, disabled, rejected) must be checked before granting access.
- Keep login audit metadata minimal (timestamp, role, outcome, device/session reference); never store passwords or PINs in logs.
- Do not expose student names, photos, DOBs, parent details, or financial information publicly without appropriate consent.
- Any account-disable, password-reset, or session-revocation action must invalidate protected access.

## 10. Implementation sequence
1. Inspect and remove existing frontend-only authentication bypasses; keep preview access clearly separate from authenticated access.
2. Resolve the trusted Firebase design for Teacher/Parent mobile + password login, school-record recovery, and single-device session enforcement.
3. Implement role-aware login and first-time account setup with Firebase Authentication.
4. Implement forgot/change password and the five-attempt / 30-second lockout.
5. Implement device-local PIN lock and app resume/reopen behavior.
6. Implement Parent multi-child linking, Teacher account lifecycle, and Alumni/Donor approval.
7. Implement role/time/language randomized welcome engine.
8. Add and verify Firestore Security Rules, then test each role and security edge cases.
9. Integrate central platform configuration and GI Super Admin settings in the previously agreed sequence.

## 11. Current repository state / known issue
At the time this specification was added, the app is still a frontend preview and Firebase is not integrated. The current login handler in js/app.js contains a demo-mode path that authenticates empty credentials, and the generic path accepts any non-empty ID/password for non-Parent roles. The Community "Open Portal Preview" action also sets the authenticated flag. These are preview shortcuts, not authentication. They must be removed or isolated behind an unmistakable preview-only mode before live authentication is enabled.
